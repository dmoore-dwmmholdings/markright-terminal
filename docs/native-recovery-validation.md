# MRK-37 app-owned native recovery validation

This research slice extends MRK-36 against pinned MRK v2 requirements R6/R7/R15. Production MRK-18/MRK-12 and the existing security, accessibility, device and release gates remain open. External-folder/provider access is not introduced.

## Recovery path

Before each debounced document-save attempt, the native session writes an exact-source checkpoint into the app-owned `.markright-recovery` directory. Only a successful file/publication-directory synchronization acknowledges a recovery copy. A document save failure leaves its checkpoint intact. The editor permits explicit Close with recovery copy only when that acknowledged checkpoint belongs to the current source revision, composition has ended and no write is active. Newer edits revoke that eligibility until their own checkpoint is confirmed.

Relaunch or explicit recovery close reveals Recovered edits in the collection browser. Its native read-only text view preserves source, supports selection, and adds no link detectors or document execution. The user chooses an existing app-owned collection and a new name. Restoration creates a separate non-clobbering file; the original saved document is untouched. The UI preserves the original `.md`/`.mrk` suffix. A successful copy receipt remains success even if later recovery cleanup or browser refresh fails.

Only an exact matching checkpoint is retired after an acknowledged document/copy save. Stale tokens, changed metadata or different source cannot retire newer recovery. An uncertain document write retains both its committed baseline and recovery checkpoint; an uncertain retirement revokes any claim that the recovery file still exists. Explicit retry can reconcile cleanup even when the document is already saved. Background flushing remains best effort.

## Disk boundary

Each open session has a UUID-named record. A new checksummed envelope is written to an exclusive UUID `.pending` file, synchronized along with the recovery directory, atomically renamed to the session record, then the directory is synchronized again. Interrupted pending files stay available to inventory; valid ones can be restored manually. No recovery is promoted automatically and no original is overwritten on open.

The binary envelope has a fixed magic/version, canonical UUIDs, bounded lengths, validated origin names, exact baseline/source UTF-8 and a SHA-256 checksum over all payload bytes. The checksum detects corruption; it is not authentication or code trust. Source and baseline are each at most 1 MiB, one envelope at most 2 MiB +1024 bytes, and the recovery directory at most 32 raw entries, including pending/malformed entries. Bounds fail explicitly rather than truncate. This is an internal recovery format, not document JSON ingestion or a portable identity manifest.

Descriptor-based access refuses symlinks and unexpected file types/links. Malformed, unsupported, unsafe and unknown entries are preserved with diagnostics while valid bounded siblings remain available. Known `.markright-write-UUID` document staging files are preserved and reported without being shown as documents. A two-link published document is readable only when the second link is a validated staging sibling with the same inode/device; arbitrary second links and all third links remain refused. Staging is bounded to 32 interrupted files and 544 total collection entries (512 documents +32 stages). Each writer reserves a staging slot before creating its temporary file, so an interrupted operation cannot exceed the scan bound. No automatic cleanup of unknown or legacy staging files is provided.
